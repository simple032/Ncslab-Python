# NCSLab Link：CUDA 仿真路径与流程（流程说明）

本文只描述**具体在做什么、先后次序如何**，不涉及函数名或类名。另有一份侧重架构与图示的说明在同一目录下的英文流程文档中，可与本文对照。

---

## 1. 两个层次：意愿 vs 真算

| 层次 | 含义 |
|------|------|
| **CUDA 意愿** | 浏览器或服务端认定「这一次仿真希望按 GPU 取向处理」：会通知前端当前后端标签是「CUDA 提示」还是「CPU」，并在服务端仿真线程里记下这个意愿。**单凭这一层不会让显卡自动算题。** |
| **真实 GPU 计算** | 可执行程序或同进程里的本地库在运行时真的去用显卡：要把 CUDA 编进产物，并在最耗时的数值步骤里走显卡路径。缺任一环节，显卡可以全程空闲。 |

---

## 2. 专节：CUDA 加速落在正常仿真的哪一环、如何体现

下面说的「正常仿真」指：已经完成代码生成与编译，进入**按时间推进、反复算方程与输出**直到结束的那一长段（不论在 Java 里积分子进程里跑，还是在本机可执行程序里跑，**形态相同**：一圈一圈推进仿真时钟）。

### 2.1 整段仿真里：哪里通常**没有**加速、哪里**才可能**有加速

```
用户点开始 → 建连接 → 校验与解析模型
        │
        ├────────────────────────────────────────────► 这些主要是 I/O、解析、会话
        │                                              与「算得更快」关系不大，
        │                                              CUDA 一般不会让这里明显变快
        ▼
生成源码、写磁盘、调用编译器得到可执行文件
        │
        ├────────────────────────────────────────────► 偶尔会因并行编译略快，
        │                                              但不是「仿真数值 CUDA」的主场
        ▼
启动仿真、建立与子进程或内部求解器的通道
        │
        ├────────────────────────────────────────────► 启动与握手本身通常不是瓶颈
        ▼
╔═══════════════════════════════════════════════════════╗
║  时间推进主循环（很多个「仿真时刻」一个接一个）         ║
║        │                                              ║
║        ├─ 每步：更新连续状态（积分/解微分方程）        ║  ◄── 常见热点之一
║        ├─ 每步：电路/代数方程、模块输出               ║  ◄── 常见热点之二（规模大时）
║        ├─ 每步：离散逻辑、事件、示波器分片写缓冲       ║  ◄── 部分可迁 GPU，部分仍宜 CPU
║        └─ 周期性：把进度或波形推给浏览器               ║  ◄── 网络与序列化；CUDA 不直接加速「发包」
╚═══════════════════════════════════════════════════════╝
        │
        ▼
写结果文件、发「结束」、关连接
        │
        └────────────────────────────────────────────► 仍以 I/O 为主
```

**结论（对应上图）：** CUDA 想体现的「加速」，几乎总是落在**灰色大框里的数值工作**——也就是**每个仿真步里重复很多次的那类计算**；而不是点按钮、生成工程、编译、或单纯为了刷新曲线而产生的网络流量。

### 2.2 放大「一步时间」里：加速**如何**接进去（文字流程图）

把主循环里的**一步**单独拿出来看，CUDA 若接入，典型接法是：**最厚的那块数值**在显卡上并行完成，结果再回到后续仍由 CPU 做的环节。

```
                本步开始（已知当前仿真时刻、状态向量等）
                        │
                        ▼
        ┌───────────────────────────────────┐
        │  可选：把本步要用的大块输入数据      │
        │  从内存拷到显存（主机 → 设备）      │  …… 有传输开销；只有计算够重才划算
        └─────────────────┬─────────────────┘
                          │
                          ▼
        ┌───────────────────────────────────┐
        │  在显卡上对大量同类运算并行求解     │  ◄── 「加速」主要发生在这里：
        │  （例如大批支路、大矩阵块、蒙特卡洛  │      同样数学工作，用大量线程同时做
        │   样本、成批参数扫描等）            │
        └─────────────────┬─────────────────┘
                          │
                          ▼
        ┌───────────────────────────────────┐
        │  把本步关键结果拷回内存（设备 → 主机）│
        └─────────────────┬─────────────────┘
                          │
                          ▼
        在 CPU 上继续做：不适合并行的控制流、与浏览器/文件的交互、
        下一步的调度、离散事件里零碎分支等
                          │
                          ▼
                    进入下一仿真时刻
```

**如何体现「真的变快了」**（可从现象上对照，仍不写具体函数名）：

| 体现方式 | 说明 |
|----------|------|
| **单步或总耗时变短** | 在模型规模、步长、精度策略不变的前提下，墙钟时间下降；这是最直接的「加速」。 |
| **同样时间内能推进更多步或更大模型** | 吞吐提高，或以前跑不动的规模现在能跑完。 |
| **系统监控里 GPU 有持续算力占用** | 仿真进行中出现与仿真进程对应的 GPU 计算或显存占用；若全程接近空闲，则数值仍在 CPU 或未走显卡路径。 |
| **曲线与指标在工程上仍可用** | 加速不应靠「算错」来变快；理想情况是与高质量 CPU 参考在允许误差内一致；若算法在 GPU 上改用近似，可能略差但更快，需在方案里说明。 |

**不会**被 CUDA 单独「加速」到很明显的部分：浏览器渲染、单次 WebSocket 文本往返的延迟、纯磁盘拷贝、以及每步里极少量分支判断——这些仍主要受 CPU、磁盘与网络约束。

### 2.3 和本仓库当前「CUDA 意愿」的关系（避免误解）

浏览器或服务端打上「希望 CUDA」标签，只影响**是否进入带 GPU 意愿的分支与提示文案**；**并不会自动把上面灰色框里的积分或电路求解搬到显卡上。** 真正要看到第二节所说的加速，还需要：生成/链接进带 CUDA 的实现，并在**时间推进循环内部**调用显卡；否则整段仿真在流程图上仍走 CPU 数值路径，只是外层多了一条「意愿」提示。

## 4. 文字流程图 B：服务端从「收到开始仿真」到「真正跑仿真」

```
WebSocket 收到一条文本消息
        │
        ▼
解析成内部用的模型与命令结构
        │
        ▼
是不是「开始仿真」命令？
   否 → 走其它业务（本文不写）
   是
        │
        ▼
根据「连的是哪条地址」和「JSON 里是否勾选希望 CUDA」
        合并判断：本次是否带 CUDA 意愿
        │
        ▼
向前端回「已开始」类状态 → 检查模型数据、用户标识、JSON 合法性
        │
        ▼
向前端回「正在生成代码」→ 按当前操作系统选用 Windows 或 Linux 下的
        仿真代码生成与编译管线，在磁盘上生成工程并生成源码
        │
        ▼
向前端回「已生成」→ 若生成阶段有错误则中断并报错
        │
        ▼
向前端回「正在编译」→ 调用本机编译链得到仿真可执行文件
        │
        ▼
向前端回「已编译」→ 再推一条带仿真时间范围的进度类消息
        │
        ▼
单独起一个后台仿真线程（带 CUDA 意愿时线程名会带 Cuda 前缀，否则带标准前缀）
        │
        └──────────► 启动该线程，主流程返回；真正耗时的仿真在线程里继续
```

说明：**生成代码、编译**这两步在目前实现里，**带不带 CUDA 意愿走的是同一套**；若要让产物里一定包含显卡代码，还要在生成 makefile 或链接选项那一层单独做分支，这是后续集成工作。

## 5. 文字流程图 C：后台仿真线程里发生什么

```
仿真线程开始
        │
        ▼
若本次带 CUDA 意愿 → 在当前线程记下「希望 CUDA」
若不带 → 不记
        │
        ▼
会话仍打开时 → 向前端发一条状态：说明当前是「仿真后端 CUDA 提示」还是「CPU」
        │
        ▼
写一行服务日志，标明这次是 CUDA 提示还是普通 CPU
        │
        ▼
执行真正的仿真：内部可能启动本机可执行子进程、通过套接字收发数据、
        把曲线等推回浏览器（与原先 CPU 仿真大框架相同）
        │
        ▼
正常结束则向前端发「仿真结束」和结果路径等
        │
        ▼
无论如何在收尾阶段：清掉本线程上的「希望 CUDA」标记、
        关闭会话、清掉线程句柄等
```

要点：

1. **「希望 CUDA」只存在当前 Java 进程里的这个仿真线程上**，不会自动跟着传给子进程；子进程若要根据开关选 GPU，需要另外在「启动子进程」时传入环境变量或命令行参数，并在子进程程序里读取——这部分需要单独接线才有。
2. 前端看到「仿真后端 CUDA 提示」只能说明 **Java 侧认定本次是 CUDA 意愿**；要确认显卡是否在算，还要看本机监控里 GPU 是否有对应进程的负载。

## 6. 文字流程图 D：从用户操作到显卡真正干活的完整目标链路

```
[浏览器]  勾选希望 CUDA 或连专用地址
      │
      ▼
[Java 服务]  解析开始仿真、生成与编译、起仿真线程、发状态与日志
      │       ↑ 当前仓库里，到这一步为止，「CUDA 意愿」已打通
      │
      │       …… 待接线：生成/编译时选用带 CUDA 的工具链与库
      ▼
[磁盘上的可执行文件]  带或不带显卡侧逻辑
      │
      │       …… 待接线：启动子进程时传入「是否用 GPU」的环境变量，
      │                 或在 Java 里通过本地库同进程调显卡
      ▼
[运行时]  CPU 做调度、网络、不适合并行的零碎逻辑；
          最重的数值循环在约定好的地方放到显卡上算，再取回结果
      │
      ▼
[浏览器]  仍通过原有 WebSocket 等通道看波形与状态
```

## 7. 文字流程图 E：同进程里的「电路 CUDA」验证库在做什么

仓库里还有一块 **native 小库**，用来在同一进程内演示「一批数据可以在 CPU 算，也可以在显卡算」，便于检查本机 CUDA 是否装对；**它不是整套电路求解**，只是数值小样例。

```
询问：当前机器上显卡是否对运行库可见？
        │
        ▼
创建计算会话：若选择「有显卡就用」且确实看得到设备，则会话标记为走显卡；
        否则整段会话走 CPU
        │
        ▼
对一批双精度数做「按比例加偏置」这类简单批量运算：
        若会话走显卡 → 把数据拷到显存 → 在显卡上并行算 → 再拷回内存；
        若会话走 CPU 或显卡步骤失败 → 改在 CPU 上算同一套公式
        │
        ▼
销毁会话：释放显存、结束显卡上下文等
```

## 8. 小结：你看到的现象分别说明什么

| 你看到的现象 | 能说明什么 | 不能说明什么 |
|--------------|------------|----------------|
| 前端状态里出现「仿真后端 CUDA 提示」 | Java 这次仿真线程按「带 CUDA 意愿」在跑 | 可执行文件或显卡里一定在做 CUDA 计算 |
| 服务日志里出现 CUDA 提示字样 | 同上 | 同上 |
| 系统监控里 GPU 利用率、显存有变化 | 机器上确实有程序在用显卡 | 一定是这次 NCSLab 仿真导致的（要对进程名和时间对齐看） |
| 同目录下自带的 bench 小工具能跑通 | 本机 CUDA 驱动与编译链大致正常 | 业务仿真已经加速 |

## 9. 代码在哪里（仅到目录粒度）

需要对照实现时：仿真入口与线程逻辑在 **Java 工程里与 WebSocket 仿真相关的包**；显卡验证库与英文流程说明在 **`native` 下的电路 CUDA 子目录**；接口约定在仓库根部的 **WebSocket API 说明文件**；可选网关片段在 **部署配置目录**。

若以后把「环境变量传给子进程」或「Java 直接调本地 CUDA 库」接上了，应回到第六节更新「待接线」两处说明。
